You are building the MVP of an autonomous hardware-recreation system for a hackathon (sponsored by Cognition, using Devin). 1. What we are building (the architecture — internalize this)
Three specialized real Devin sessions collaborate on each chip, coordinated by a Python orchestrator that we control (NOT a Devin). Devin sessions are isolated cloud VMs and cannot talk to each other — so the git repository is the shared bus. Every handoff between agents is a git commit on a per-attempt branch.
For one chip attempt, on a dedicated branch (e.g. attempt/74138-01):
Coder-Devin — task: implement the spec as /rtl/<chip>.v, commit, push.
The orchestrator runs our harness: compiles the RTL with Icarus Verilog and checks it against our human-authored golden vectors. The orchestrator, via the harness, is the ONLY source of pass/fail truth. No Devin ever decides correctness.
On FAIL → send the failing vectors back to Coder-Devin, loop (capped, see §4).
On PASS → advance the branch.
Testbencher-Devin — task: ADD extra edge-case testbench coverage beyond the golden vectors, commit. Its tests can catch more, but can NEVER override the golden vectors as the source of truth. The orchestrator re-runs the harness after.
Style-Devin — task: clean formatting/naming/comments in the RTL WITHOUT changing behavior, commit. The orchestrator re-runs the harness to confirm behavior is unchanged.
Final commit on the branch = the verified, clean design. Then run Yosys synthesis targeting a real FPGA architecture (iCE40 via synth_ice40 by default) to produce a device-specific resource report (e.g. LUT4 count for the iCE40) as proof it is real, FPGA-buildable hardware — not an abstract gate count.
Parallelism / "swarm": we run this whole 3-Devin pipeline across MULTIPLE attempts at once (multiple branches). Concurrency is across attempts, not within one. A later stage adds a leaderboard comparing the parallel implementations.
Why FPGA (the delivery context — informs the code, not just the pitch): the target is a drop-in replacement for a discontinued chip. Re-fabricating silicon needs masks and a foundry — millions of dollars, low-volume-hostile. An FPGA is commodity silicon reconfigured post-purchase: no fab, reprogrammable in the field, and matched to the defense market's low-volume/high-mix reality. So the pipeline's output must be a design proven to map onto a real FPGA — that is why synthesis is FPGA-targeted (§2), and why the resource report is device-specific. The MVP proves the design + verification step (spec → verified, FPGA-synthesizable RTL). It does not flash a physical board — we have no board, and physical qualification/certification are explicitly out of scope (§5). Keep that boundary crisp: "FPGA-ready and FPGA-synthesized," never "flashed onto hardware."
Non-negotiable design principles:
Humans own the golden vectors. They are the ground truth. No Devin writes or edits them.
Instrument the harness, not the agent. All UI state comes from structured events our harness/orchestrator emit, and from Devin's structured_output field — NEVER from parsing a Devin session's natural-language chatter.
Verify exhaustively where the input space is small enough (both our chips qualify), so there is nothing for a Devin to "overfit" to. Do not expose only a subset of vectors that a Devin could hard-code against.

2. Tech stack (fixed — do not substitute)
Orchestrator + harness: Python 3.
Backend/event server: FastAPI, streaming events to the UI over SSE.
UI: React + Vite. It must look like a clean, dark, mission-control / defense-console "command room" — pipeline graph of the three agents with animated handoffs, live per-agent status, and a proof panel (vector pass count, waveform, synthesis numbers). Clean and sharp.
EDA toolchain (CLI): Icarus Verilog (iverilog + vvp) for simulation, Yosys for synthesis. Yosys must target a real FPGA architecture — default iCE40 (synth_ice40); keep the target configurable (e.g. synth_ecp5) via one setting. Parse the device-specific resource report (LUT4 count, etc.) — this is the "FPGA-ready hardware" proof.
Optional / stretch, only if explicitly approved later: nextpnr place-and-route to get real timing (Fmax) for an FPGA part. This is the ONLY way to get true Fmax — do NOT report Fmax from synthesis alone or invent it. Until nextpnr is added, the leaderboard compares LUT/resource count only, not timing.
Assume all tools are installed locally on PATH. Do NOT build a Docker image — we handle containerization later. If a tool is missing, report it at the Stage 0 check.
Devin: the official REST API only.
Base: https://api.devin.ai/v1
Auth: Authorization: Bearer $DEVIN_API_KEY — read the key from the DEVIN_API_KEY env var. NEVER hardcode it or print it.
Create a session: POST /sessions with a JSON prompt → returns session_id and url.
Poll a session: GET /session/{session_id} → returns status_enum (running | blocked | stopped) and a structured_output object. Poll with backoff.
Ask Devin tasks to emit their result into structured_output (e.g. commit SHA, files changed) so the orchestrator reads structured data, not prose.

4. Guardrails (hard limits — implement these before any real Devin call)
Max 6 attempts per chip. After 6 failing Coder iterations, stop that branch and report.
~15 min wall-clock timeout per Devin session. On timeout, mark the session stalled, emit an event, and stop that branch cleanly — never hang the UI on a frozen session.
Global session ceiling: a configurable cap on total concurrent + total lifetime Devin sessions per run (default: max 4 concurrent, max 20 total per run) so a runaway loop cannot burn the token budget. Refuse to exceed it and report.
Every failure is visible, never silent. A stalled/errored/blocked session must surface in the UI as that state, with its session_url, not as a spinner that never resolves.
No mock/fake solver. The coding loop is driven by the real Devin API, period. (Failure states are made visible per above; they are not faked away.)

5. Scope walls (do NOT do any of these — refuse and flag if asked)
No analog / mixed-signal / RF / power / rad-hard parts. Digital logic with a published, golden-model-able spec ONLY.
No physical FPGA flashing / no real board. FPGA-targeted synthesis (and, only if later approved, place-and-route) is in scope; putting a bitstream on hardware is NOT.
No Docker (later).
No certification/qualification logic or claims.
No chip beyond the two specified (74138, 82S100) in this build.
No letting any Devin author or modify golden vectors.
No parsing Devin natural-language output for pipeline state.
No scope additions of any kind without asking first.

6. Primary chip — the 74138 (3-to-8 line decoder/demux)
This is the priority target; get the whole pipeline working on it first.
Spec (this is the golden truth to encode in /spec/chips/74138.py):
Inputs (6 total): A0, A1, A2 (3-bit select), plus enables G1 (active HIGH), G2A_n (active LOW), G2B_n (active LOW).
Outputs: Y0..Y7, active LOW.
Behavior: the decoder is enabled only when G1 == 1 AND G2A_n == 0 AND G2B_n == 0.
When enabled: output Y[sel] is driven LOW (0), all other outputs HIGH (1), where sel = {A2,A1,A0}.
When NOT enabled: ALL outputs HIGH (1).
Input space = 2^6 = 64 combinations → verify EXHAUSTIVELY. Generate all 64 golden vectors; the design must pass all 64.
Note the natural bug surface (active-low outputs + 3-term enable) — a first-pass RTL that gets polarity or enable logic wrong is expected, and driving the real fail→fix loop is the point. Do NOT seed a fake bug; let the real loop earn it.

7. Second chip — the 82S100 (16-in / 8-out FPLA), as an address decoder
Secondary target; wire it in as a second registry config once 74138 works.
Chosen programmed instance (encode in /spec/chips/82s100.py):
16 address inputs A0..A15, 8 outputs Y0..Y7 active LOW (chip-selects).
Default function: decode the top 3 address bits A[15:13] into 8 regions — Yi_n = 0 when A[15:13] == i, else 1. To exercise real sum-of-products behavior, make at least one output active for TWO disjoint ranges (a genuine 2-product-term output) rather than a single contiguous region. Keep it simple and fully documented in the file.
Input space = 2^16 = 65,536 → verify EXHAUSTIVELY.
Framing (for our reference, not for code): this is the real part a Navy contractor is recreating; exhaustive equivalence over all 65,536 inputs is the rigor claim.
